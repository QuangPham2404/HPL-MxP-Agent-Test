# TASK-3X4-000 — Phase 0: 3×4 GAAS Baseline

## 1. STRATEGIC SPECIFICATION

### 1.1 Objective

Establish one valid immutable original baseline for the new **3 GAAS nodes × 4 H200 GPUs/node** HPL-MxP optimization track.

This is a fast Phase-0 baseline task, not a tuning task. Reuse the extensive existing 3×4 GAAS characterization and validated multinode launch/communication evidence rather than repeating comprehensive probes.

Run **one scored baseline attempt**. If it completes normally with finite correctness evidence and `PASSED`, designate that attempt immediately as the immutable `3x4-GAAS` original baseline. No repeat/noise study is required.

No optimization analysis or next-direction selection is part of this task.

### 1.2 Context

Historical 3×4 GAAS work already establishes:

- a working 3-node × 4-GPU, 12-rank container-MPI + pbsdsh launch path;
- correct one-rank-per-GPU operation;
- substantial same-topology correctness and memory-envelope evidence through at least `N=510000` under the older `NB=1024, 3×4 row` diagnostic protocol;
- a strong node-condition effect for partial-node 3×4 jobs, making pre-submit contention control essential;
- validated GPUDirect/NCCL operation when the RoCE bond is excluded from NCCL HCA selection; and
- the current NVIDIA HPC Benchmarks v26.02 container and GAAS multinode execution mechanism.

The new baseline intentionally uses a more 2×8-comparable provisional geometry:

```text
N = 480000
NB = 3072
NPROW = 4
NPCOL = 3
NPORDER = column
```

`NB=3072` and `4×3 column` are **provisional Phase-0 controls**, not transferred 3×4 optima. They remain open for later independent tuning.

The historical `3x4-baseline_v1` and clean-node diagnostic N-sweep are prior evidence only. Neither becomes the denominator for this new campaign. Only the first valid scored run produced by this task becomes the immutable `3x4-GAAS` baseline.

### 1.3 Strategic Question

Can the fixed current-protocol configuration below complete correctly on a low-contention 3×4 GAAS allocation and provide the immutable original baseline for the new 3×4 optimization track?

This is an execution question only. Codex must not tune or re-derive the configuration.

#### B. Fixed fast-baseline configuration

Use exactly these HPL-MxP scientific controls:

```text
--n 480000
--nb 3072
--nprow 4
--npcol 3
--nporder column
--gpu-affinity 0:1:2:3

--sloppy-type FP16
--use-mpi-panel-broadcast 0
--use-separate-stream-for-gemm 1
--prioritize-trsm 0
--prioritize-factorization 0

--test-loop 1
--skip-tests 0
--monitor-gpu 0
```

Use the validated NCCL bond-exclusion setting:

```text
NCCL_IB_HCA=mlx5_0,mlx5_1,mlx5_2,mlx5_3,mlx5_4,mlx5_5,mlx5_8,mlx5_9
```

Forward it to all MPI ranks. This is treated as a validated 3×4 platform/transport correctness setting, not as a tuning variable.

Do **not** introduce an OMP/CPU/memory-affinity tuning choice in this baseline task. Preserve the current/default host-runtime state and explicitly record the effective values of `OMP_NUM_THREADS`, `OMP_PLACES`, and `OMP_PROC_BIND` (including `unset`). Host-runtime tuning remains downstream work.

#### C. New 3×4 campaign layout

Create and use:

with the normal experiment structure: README, reusable PBS script(s), and `outputs/`.

This task-specific Human-approved path supersedes the older root-`AGENTS.md` note that directed new 3×4 work to `experiments/3Nodes-4GPUs/`. Historical directories remain untouched.

The persistent campaign analysis path is:

`planning/3x4-GAAS.md`

but Codex must **not** create strategic conclusions there during execution. It will be created/updated by the Strategic Analyst only after explicit `ANALYSE_RESULTS` authorization.

#### D. Pristine-node selection and contention evidence

Immediately before submission:

1. run `pbsnodes -aSj`;
2. inspect eligible nodes in **both `gpu_as` and `gpu_ded`**;
3. choose the single eligible three-node set, within one queue, with the lowest observable contention;
4. host-pin the submission to that trio; and
5. preserve the scheduler snapshot and record the selected queue/nodes plus the observable contention state for each selected node.

Record enough information from the snapshot to support later interpretation if performance is degraded, including available/total CPU and GPU resources and visible job/co-tenant information when emitted.

Do not mix nodes belonging to different queue/Qlist domains in one job. If no perfectly pristine trio exists, choose the least-contended eligible trio and record the remaining contention; lack of a perfectly pristine trio is not by itself a reason to wait indefinitely or submit repeated baseline attempts.

#### E. One scored baseline attempt

Submit exactly one scientific/scored baseline attempt using:

- 3 nodes × 4 H200 GPUs;
- 12 MPI ranks;
- one rank/GPU;
- `place=scatter`;
- no `mpiprocs`;
- host-pinned chunks selected under Section 1.4D;
- the validated per-node request shape `ngpus=4:ncpus=48:mem=1000GB`;
- a de-duplicated hostfile with `slots=4`;
- NVIDIA HPC Benchmarks v26.02 container;
- container MPI end-to-end through the validated pbsdsh bridge;
- project `hpc_ebslee`;
- queue `gpu_as` or `gpu_ded`;
- the fixed controls in Section 1.4B; and
- `--skip-tests 0 --monitor-gpu 0`.

If the run completes normally and reports a finite correctness result with `PASSED`, it becomes the immutable `3x4-GAAS` original baseline immediately.

**No second scored run is allowed or required in this task.**

A retry is allowed only if the submitted attempt fails before producing a meaningful scientific benchmark result because of a clearly deterministic Track-1 workflow/scheduler/path/output defect. Preserve the failed attempt under a new unique label. Do not rerun a genuine OOM, correctness failure, MPI/NCCL failure, hang, or unexpectedly poor but valid performance result without new strategic direction.

#### F. Minimum evidence required

Preserve:

- attempt ID and PBS job ID;
- pre-submit `pbsnodes -aSj` snapshot;
- selected queue and three nodes;
- recorded per-node contention state;
- exact resource request;
- exact HPL-MxP command/flags;
- effective `NCCL_IB_HCA`;
- effective OMP environment;
- execution-tree revision/path;
- rank/node/GPU mapping sufficient to confirm 12 ranks, 4 ranks/node, one rank/GPU;
- PBS exit state;
- HPL-MxP final correctness/verification result;
- finite residual/normalized residual when emitted;
- LU time/GFLOP/s when emitted;
- iterative-refinement timing/iterations when emitted;
- overall GFLOP/s;
- relevant host/device memory headroom when emitted; and
- stdout/stderr.

Existing 3×4 characterization/provenance may be referenced rather than duplicated.
