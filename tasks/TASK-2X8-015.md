## 1. STRATEGIC SPECIFICATION

### 1.1 Objective

Complete Phase 4 communication-flag work on the retained 2x8 GAAS stack with
one bounded sequential task:

~~~text
Stage A — quick UCX transport-family characterization
    AUTO -> RC -> RC-X -> DC -> UD -> AUTO

mechanical gate

Stage B — U-panel chunk sweep
    8 control -> 2 -> 4 -> 16 -> 8 control
~~~

Stage A is **not a deep UCX tuning campaign**. Its purpose is to answer:

> Does UCX AUTO already choose a sensible transport family for this workload,
> or does forcing one major inter-node family produce an unexpected material
> improvement?

If the transport characterization behaves as expected, close UCX transport
selection at AUTO and automatically continue to the U-panel sweep.

If a forced transport family materially and repeatably beats AUTO under the
pre-authorized gate below, stop before changing U-panel chunking and hand the
unexpected dependency back for strategic investigation.

No recursive transport search, transport-list combinatorics, protocol-threshold
tuning, or profiler work is authorized.

### 1.3 Strategic Questions / Hypotheses

#### Question A — UCX transport family

> If one major UCX inter-node family is isolated at a time, does any explicit
> family materially outperform AUTO?

Expected result:

~~~text

~~~

If that occurs, retain AUTO and proceed.

The test deliberately avoids combining competing inter-node families such as:


inter-node family.

#### 1.6C. Stage A -> Stage B transition logic

This transition is deterministic and intentionally asymmetric.

##### Step 1 — validate AUTO bracket

Both T0a and T0b must be valid PASSED controls.

For LU and overall performance, calculate:

~~~text
AUTO_midpoint = (T0a + T0b) / 2

LU_bracket_spread_pct
overall_bracket_spread_pct
~~~

Define:

~~~text
local_noise_pct
  = max(0.5%,
        LU_bracket_spread_pct,
        overall_bracket_spread_pct)

positive_surprise_threshold_pct
  = max(2.0%, 2 * local_noise_pct)
~~~

The 2% floor follows the existing campaign materiality convention.

If either AUTO bracket spread exceeds 5%, stop before Stage B and report an
unstable transport-control stage. Do not rerun Stage A automatically.

##### Step 2 — classify explicit families

For every valid explicit transport arm calculate delta versus AUTO midpoint.

A **material positive surprise** exists only when an explicit family satisfies
both:

~~~text
LU improvement >= positive_surprise_threshold_pct

AND

overall improvement > local_noise_pct
~~~

Correctness, iterations, and memory regime must also remain valid.

This is a transition gate, not a campaign winner declaration.

##### Step 3 — transition

If **any** valid explicit family is a material positive surprise:

~~~text
STOP TASK BEFORE STAGE B
~~~

Complete the fixed Stage-A characterization first, preserve all evidence, and
report the unexpected family/families. Do not profile or investigate further
inside this task.

If no explicit family materially beats AUTO:

~~~text
retain AUTO for execution purposes
proceed automatically to Stage B
~~~

This includes all of the following expected outcomes:

- explicit RC/RC-X ~= AUTO;
- explicit family is slightly better but below material threshold;
- explicit family is slower than AUTO;
- supported DC/UD are worse;
- optional RC-X/DC/UD family is unavailable and was cleanly skipped.

Do not request human input merely because explicit candidates tie, regress, or
are unsupported.

At least one valid explicit RC-family point (T1 or T2) plus a valid AUTO
bracket is required to characterize Stage A sufficiently for automatic
progression. If no RC-family explicit point can run, stop before Stage B and
report the capability gap.

#### 1.6E. Node and queue selection — user override

For this task, node selection uses the combined eligible pool:

~~~text
gpu_as UNION gpu_ded
~~~

**There is no strategic requirement that the two selected nodes carry the same
nominal queue label.** Codex may combine any two clean eligible 8-GPU nodes
drawn from `gpu_as` and `gpu_ded`, subject only to PBS being able to grant
them together in one legal multinode allocation.

Immediately before submission:

1. run `pbsnodes -aSj`;
2. consider clean eligible 8-GPU nodes from both `gpu_as` and `gpu_ded`;
3. prefer the cleanest pair from the combined pool;
4. determine a legal PBS submission queue/resource request that can co-allocate
   both selected hosts.

Historical GAAS evidence shows that some hosts with disjoint queue membership
may not be co-allocatable under one PBS `-q` queue. If the cleanest nominally
mixed pair cannot be allocated together:

> do **not** stop, ask the user, or loop on that pair.

Instead choose the next-cleanest schedulable pair from the same combined
`gpu_as ∪ gpu_ded` pool.

A same-queue pair is therefore an operational fallback when required by PBS,
not a scientific requirement.

Prefer one same-allocation job for Stage A and, if the gate passes, Stage B.
If operational recovery requires a new allocation, preserve fresh AUTO/chunk
control brackets in the new allocation and document the change.

### 1.10 Strategic Analyst Notes

Stage A should be interpreted as characterization, not a search for a UCX
winner.

The prior expectation is:

~~~text
AUTO already selects rc_mlx5 + zero-copy
=> explicit RC-family restriction should be similar or worse
=> DC/UD should not materially improve this 2-node/16-rank workload
~~~

Because panel broadcast is fixed at NCCL (`use-mpi-panel-broadcast=0`),
UCX_TLS may have only secondary influence on the main LU panel path. A flat
Stage-A result is therefore useful closure, not a failed experiment.

A slower explicit family does not justify investigation. It simply demonstrates
that removing AUTO's flexibility is unhelpful.

Only a material positive explicit-family result changes the dependency state.
If that occurs, stop before U-panel chunking. Detailed causal work
(Nsight Systems first, then lower-level transport investigation if justified)
is intentionally deferred.

If Stage A closes normally, Stage B asks a separate scheduling/readiness
question under the retained communication stack:

> With NCCL panel broadcast and AUTO UCX fixed, does U-panel chunk granularity
> expose better overlap/readiness?

Do not form a transport x chunk Cartesian product.
