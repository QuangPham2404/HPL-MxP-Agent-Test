## 1. STRATEGIC SPECIFICATION

### 1.1 Objective

Begin blueprint **Phase 4 — Communication** on the retained 2x8 GAAS HPL-MxP
stack with a bounded **Phase 4A characterization task**.

This task does **not tune communication parameters**. Its purpose is to
establish what the retained Phase-3 control actually does on the communication
critical path before Phase 4B changes transport or panel policy.

Specifically, determine and preserve:

1. the clean Phase-4 reference performance under the retained Phase-3 stack;
2. the actual MPI/UCX transport/protocol/lane behavior exercised by HPL-MxP;
3. the actual NCCL network backend, HCA/channel usage, and GPUDirect-RDMA
   participation exercised by HPL-MxP;
4. per-HCA InfiniBand traffic, rail balance, wait/congestion indicators, and
   link/error state;
5. whether the current automatic communication path is sufficiently understood
   to design Phase 4B `UCX_TLS x --use-mpi-panel-broadcast` candidates without
   guessing.

The task consists of:

~~~text
A0 — clean retained HPL-MxP control
A1 — exact diagnostic clone with communication-path logging

Conditional only if A1 is transfer-level ambiguous:
A2-U — MPI/UCX GDR-off diagnostic clone
A2-N — NCCL GDR-off diagnostic clone
~~~

A2-U and A2-N are stack-specific diagnostics. Never disable both stacks in one
arm because that would destroy attribution.

No Phase 4B or 4C tuning is authorized.

### 1.3 Strategic Questions / Hypotheses

#### Question A — Clean communication reference

> Under the final retained Phase-3 stack, what are the clean end-to-end,
> LU, IR, memory, and fabric-traffic characteristics that Phase 4B/4C must
> compare against?

Hypothesis:

- A0 should remain in the established low-IR regime;
- communication evidence should primarily explain LU-side behavior;
- HCA traffic should show a stable multinode pattern with no link/error
  pathology.

#### Question B — MPI/UCX fast path

> What transport, protocol, rendezvous/staging behavior, HCA(s), and lane
> distribution does the HPL-MxP application actually exercise through
> MPI/UCX?

Required distinction:

~~~text
capability evidence
!=
measured-transfer evidence
~~~

For example, CUDA-aware MPI, visible mlx5 devices, or a loaded peer-memory
module are not enough by themselves. Prefer transfer-level evidence such as
the actual selected UCX transport/protocol and zero-copy versus host-staged
path.

Hypothesis:

- the retained application should use the container HPC-X / UCX fast path;
- if GPU-buffer inter-node UCX traffic is exercised, transfer-level logs should
  identify whether it uses zero-copy RDMA or a `cuda_copy`/host-staged path.

#### Question C — NCCL fast path

> What NCCL network backend and inter-node channel topology does HPL-MxP
> actually use, and what fraction of inter-node IB channels are marked
> GDRDMA?

Hypothesis:

- panel-broadcast=0 should exercise a meaningful NCCL panel path;
- the run should use the expected IB backend rather than Socket/TCP fallback;
- GDR may be partial across channels, so record a **GDRDMA channel fraction**
  rather than a Boolean only.

#### Question D — Rail use

> How much traffic does each physical HCA carry, how balanced is the traffic,
> and do any rails show wait/error/congestion evidence?

This is explanatory evidence, not an optimization objective. Perfectly equal
rail use is not assumed to be optimal.

- a simple rail-imbalance summary such as max-rail / mean-rail traffic and/or


- A0 fails correctness, OOMs, has non-finite residual, or cannot reproduce the
  retained scientific settings;
- the allocated shape/rank map differs from 2 nodes x 8 ranks/node;
- OMP=4 cannot be verified on every rank;
- same-allocation comparability is lost after A0;
- an HCA/link is down or has a material unexpected error state;
- the selected communication path unexpectedly uses Socket/TCP fallback,

  the exact A2-U/A2-N diagnostic logic;
- A2-U or A2-N fails to change the targeted stack in the expected diagnostic
  direction;
- resolving ambiguity would require another UCX/NCCL knob, microbenchmark,
  profiler, rail filter, UCC change, or transport restriction;
- execution would require Phase 4B/4C tuning.

A surprising scientific result is not authorization to tune around it.

### 1.10 Strategic Analyst Notes

Phase 4A is **characterization**, not a winner-selection experiment.

Interpret A0 as the clean Phase-4 reference. Treat A1 and any A2 arm only as
mechanism evidence.

The key reading order after execution should be:

~~~text
1. correctness + retained settings
2. A0 end-to-end / LU / IR reference
3. MPI/UCX actual application path
4. NCCL actual application path + GDRDMA fraction
5. per-HCA traffic and wait/error evidence
6. rank/rail imbalance
7. decide whether Phase 4B can be designed directly
~~~

Important prior-debug lessons to preserve:

- container GDR capability has been demonstrated historically, but current
  HPL-MxP application use still needs direct evidence;
- `UCX_PROTO_INFO=y` plus `UCX_LOG_LEVEL=info` is more informative than
  capability-only checks for zero-copy versus staged behavior;
- NCCL GDR can be partial across channels; preserve the fraction;
- per-HCA GDR capability messages alone are not proof of transfer-level GDR;
- message size / rendezvous behavior can materially affect communication
  performance even when GDR is functional, so the UCX protocol evidence from
  4A may become important context for later U-panel chunk analysis;
- asymmetric rail use is not itself a reason to reopen `--ucx-affinity`.

After authorized analysis, the next action may be a bounded Phase-4B
`UCX_TLS x --use-mpi-panel-broadcast` screen, but 4A does not authorize or
preselect those values.
