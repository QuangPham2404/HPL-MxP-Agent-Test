## 1. STRATEGIC SPECIFICATION

### 1.1 Objective

Begin blueprint **Phase 4 — Communication** on the retained 2x8 GAAS HPL-MxP
stack with a bounded **Phase 4A characterization task**.

This task does **not tune communication parameters**. Its purpose is to
establish what the retained Phase-3 control actually does on the communication
critical path before Phase 4B changes transport or panel policy.

Specifically, determine and preserve:

1. the clean Phase-4 reference performance under the retained Phase-3 stack;
2. the actual MPI/UCX transport/protocol/lane behavior exercised by HPL-MxP;
3. the actual NCCL network backend, HCA/channel usage, and GPUDirect-RDMA
   participation exercised by HPL-MxP;
4. per-HCA InfiniBand traffic, rail balance, wait/congestion indicators, and
   link/error state;
5. whether the current automatic communication path is sufficiently understood
   to design Phase 4B `UCX_TLS x --use-mpi-panel-broadcast` candidates without
   guessing.

The task consists of:

~~~text
A0 — clean retained HPL-MxP control
A1 — exact diagnostic clone with communication-path logging

Conditional only if A1 is transfer-level ambiguous:
A2-U — MPI/UCX GDR-off diagnostic clone
A2-N — NCCL GDR-off diagnostic clone
~~~

A2-U and A2-N are stack-specific diagnostics. Never disable both stacks in one
arm because that would destroy attribution.

No Phase 4B or 4C tuning is authorized.

### 1.3 Strategic Questions / Hypotheses

#### Question A — Clean communication reference

> Under the final retained Phase-3 stack, what are the clean end-to-end,
> LU, IR, memory, and fabric-traffic characteristics that Phase 4B/4C must
> compare against?

Hypothesis:

- A0 should remain in the established low-IR regime;
- communication evidence should primarily explain LU-side behavior;
- HCA traffic should show a stable multinode pattern with no link/error
  pathology.

#### Question B — MPI/UCX fast path

> What transport, protocol, rendezvous/staging behavior, HCA(s), and lane
> distribution does the HPL-MxP application actually exercise through
> MPI/UCX?

Required distinction:

~~~text
capability evidence
!=
measured-transfer evidence
~~~

For example, CUDA-aware MPI, visible mlx5 devices, or a loaded peer-memory
module are not enough by themselves. Prefer transfer-level evidence such as
the actual selected UCX transport/protocol and zero-copy versus host-staged
path.

Hypothesis:

- the retained application should use the container HPC-X / UCX fast path;
- if GPU-buffer inter-node UCX traffic is exercised, transfer-level logs should
  identify whether it uses zero-copy RDMA or a `cuda_copy`/host-staged path.

#### Question C — NCCL fast path

> What NCCL network backend and inter-node channel topology does HPL-MxP
> actually use, and what fraction of inter-node IB channels are marked
> GDRDMA?

Hypothesis:

- panel-broadcast=0 should exercise a meaningful NCCL panel path;
- the run should use the expected IB backend rather than Socket/TCP fallback;
- GDR may be partial across channels, so record a **GDRDMA channel fraction**
  rather than a Boolean only.

#### Question D — Rail use

> How much traffic does each physical HCA carry, how balanced is the traffic,
> and do any rails show wait/error/congestion evidence?

This is explanatory evidence, not an optimization objective. Perfectly equal
rail use is not assumed to be optimal.

### 1.4 Required Evidence / Deliverables

#### A. Benchmark scorecard

For A0 preserve:

- overall HPL-MxP GFLOP/s;
- percentage versus immutable original 2x8 baseline where the normal results
  pipeline provides it;
- LU time and LU GFLOP/s;
- IR / solver time;
- IR/LU ratio;
- refinement iteration count;
- finite residual and PASSED/FAILED;
- host/device memory consumption and headroom;
- total arm wall-clock;
- any application-emitted per-rank or AVG/MAX/MIN timing / imbalance markers,
  including the owning rank where available;
- exact effective scientific controls;
- verified `OMP_NUM_THREADS=4` on all 16 ranks;
- global/local rank -> node -> GPU map;
- PBS job/node/queue/timestamps/exit status.

Collect the same benchmark fields for diagnostic arms, but **A1/A2 performance
is diagnostic only** because logging or forced-path controls can perturb
timing. Do not rank A1/A2 against A0 as optimization candidates.

#### B. Per-HCA InfiniBand evidence — required around every executed arm

For every physical HCA on both allocated nodes capture pre/post values and
compute arm deltas for, where exported by the device:

~~~text
port_xmit_data
port_rcv_data
port_xmit_wait
discard counters
symbol / link error counters
link recovery / reset counters
constraint / receive / transmit error counters
~~~

At minimum derive:

- TX bytes per HCA;
- RX bytes per HCA;
- total TX/RX per node;
- traffic share per HCA;
- `port_xmit_wait` delta;
- any nonzero/new error, discard, recovery, or constraint counter;
- a simple rail-imbalance summary such as max-rail / mean-rail traffic and/or
  coefficient of variation across the eight physical HCAs.

Use the expected physical IB devices:

~~~text
mlx5_0
mlx5_1
mlx5_2
mlx5_3
mlx5_4
mlx5_5
mlx5_8
mlx5_9
~~~

Do not silently include a bond or unexpected RoCE path as if it were normal.
If NCCL/UCX selects an unexpected bond/device/link family, preserve the
evidence and apply the stop/escalation rules.

Per-HCA bytes and rail balance are **explanatory metrics**, not winner metrics.

#### C. MPI/UCX transfer-path evidence — A1

A1 must enable targeted communication diagnostics sufficient to establish the
application path without per-message debug flooding:

~~~text
UCX_LOG_LEVEL=info
UCX_PROTO_INFO=y
~~~

Forward the variables explicitly to every MPI rank through the validated
launcher and verify their effective values.

Preserve raw logs and extract at minimum:

- PML / UCX path actually selected;
- effective `UCX_TLS` state (expected unset/automatic in 4A);
- effective `UCX_NET_DEVICES` state;
- selected UCX transport(s);
- selected protocol / rendezvous behavior for relevant GPU-buffer traffic when
  exposed;
- zero-copy GPU-buffer path versus `cuda_copy` / host-staged evidence;
- selected HCA(s) / lanes and any observable lane distribution;
- transport fallback/warning messages.

Do not claim GPUDirect RDMA from capability messages alone.

#### D. NCCL transfer-path evidence — A1

A1 must enable targeted NCCL diagnostics using the previously validated style,
for example:

~~~text
NCCL_DEBUG=INFO
NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,ENV,NET,GRAPH,P2P,COLL,SHM,TUNING
~~~

or the installed-release equivalent if exact accepted spelling differs.

Preserve raw logs and extract at minimum:

- NCCL network backend/plugin;
- expected IB versus Socket/TCP fallback;
- physical HCA selection;
- total inter-node IB channel count observable from the diagnostic output;
- inter-node channels tagged `GDRDMA`;
- **GDRDMA fraction = GDRDMA-tagged inter-node channels / total inter-node IB
  channels**;
- channel/HCA distribution when extractable;
- unexpected bond/RoCE/mixed-link warnings;
- topology/graph or connection warnings relevant to the actual measured run.

A per-HCA message saying GDR is supported is not sufficient evidence that a
measured transfer used GDR. Prefer per-channel / transfer-path evidence.

#### 1.6D. Conditional A2-U — MPI/UCX GDR-off diagnostic

Run A2-U **only if A1 cannot determine the MPI/UCX application transfer path
with transfer-level evidence** and a GDR-off A/B is required to resolve that
specific ambiguity.

A2-U keeps the exact A1 diagnostics and all HPL scientific controls unchanged,
then adds only the previously validated MPI/UCX diagnostic control:

~~~text
UCX_IB_GPU_DIRECT_RDMA=n
~~~

Forward and verify the variable on every rank.

Purpose:

- test whether the UCX application path visibly switches from a zero-copy
  GPU-RDMA protocol to `cuda_copy` / host staging or another documented
  non-GDR path;
- confirm that the diagnostic knob changes the intended stack.

A2-U is **not a performance candidate** and does not authorize UCX transport
tuning.

Do not run A2-U merely because A1 performance is unexpected if A1 already
provides conclusive transfer-path evidence. Preserve the anomaly for strategic
analysis instead.

#### 1.6E. Conditional A2-N — NCCL GDR-off diagnostic

Run A2-N **only if A1 cannot determine NCCL GDR participation with
transfer/channel-level evidence** and a GDR-off A/B is required to resolve that
specific ambiguity.

A2-N keeps the exact A1 diagnostics and all HPL scientific controls unchanged,
then adds only the previously validated NCCL diagnostic control:

~~~text
NCCL_NET_GDR_LEVEL=LOC
~~~

or the exact equivalent confirmed by the installed NCCL stack if syntax has
changed.

Forward and verify the variable on every rank.

Purpose:

- test whether GDRDMA-tagged inter-node channels drop to zero or otherwise
  switch in the expected way while retaining the same underlying IB backend;
- confirm that the diagnostic knob changes the intended NCCL path.

A2-N is **not a performance candidate** and does not authorize NCCL transport
or topology tuning.

#### 1.6F. Conditional-arm logic

After A1:

1. If MPI/UCX transfer-level evidence is conclusive, **skip A2-U**.
2. If NCCL transfer/channel-level evidence is conclusive, **skip A2-N**.
3. If only MPI/UCX is ambiguous, run only A2-U.
4. If only NCCL is ambiguous, run only A2-N.
5. If both are ambiguous, A2-U and A2-N may both run sequentially, but as
   separate arms with only one stack's GDR-off control changed per arm.
6. Never create a combined MPI+NCCL GDR-off arm.
7. After the authorized conditional arm(s), stop. Do not add further
   diagnostics without human approval.

Maximum HPL arms authorized by this task: four
(`A0 + A1 + A2-U + A2-N`).

### 1.9 Stop / Escalation Conditions

Stop and preserve evidence without expanding scope if:

- A0 fails correctness, OOMs, has non-finite residual, or cannot reproduce the
  retained scientific settings;
- the allocated shape/rank map differs from 2 nodes x 8 ranks/node;
- OMP=4 cannot be verified on every rank;
- same-allocation comparability is lost after A0;
- an HCA/link is down or has a material unexpected error state;
- the selected communication path unexpectedly uses Socket/TCP fallback,
  mixed RoCE/IB behavior, an unexpected bond device, or another topology that
  would require a mitigation/configuration change;
- A1 reveals a surprising communication mechanism that cannot be resolved by
  the exact A2-U/A2-N diagnostic logic;
- A2-U or A2-N fails to change the targeted stack in the expected diagnostic
  direction;
- resolving ambiguity would require another UCX/NCCL knob, microbenchmark,
  profiler, rail filter, UCC change, or transport restriction;
- execution would require Phase 4B/4C tuning.

A surprising scientific result is not authorization to tune around it.

### 1.10 Strategic Analyst Notes

Phase 4A is **characterization**, not a winner-selection experiment.

Interpret A0 as the clean Phase-4 reference. Treat A1 and any A2 arm only as
mechanism evidence.

The key reading order after execution should be:

~~~text
1. correctness + retained settings
2. A0 end-to-end / LU / IR reference
3. MPI/UCX actual application path
4. NCCL actual application path + GDRDMA fraction
5. per-HCA traffic and wait/error evidence
6. rank/rail imbalance
7. decide whether Phase 4B can be designed directly
~~~

Important prior-debug lessons to preserve:

- container GDR capability has been demonstrated historically, but current
  HPL-MxP application use still needs direct evidence;
- `UCX_PROTO_INFO=y` plus `UCX_LOG_LEVEL=info` is more informative than
  capability-only checks for zero-copy versus staged behavior;
- NCCL GDR can be partial across channels; preserve the fraction;
- per-HCA GDR capability messages alone are not proof of transfer-level GDR;
- message size / rendezvous behavior can materially affect communication
  performance even when GDR is functional, so the UCX protocol evidence from
  4A may become important context for later U-panel chunk analysis;
- asymmetric rail use is not itself a reason to reopen `--ucx-affinity`.

After authorized analysis, the next action may be a bounded Phase-4B
`UCX_TLS x --use-mpi-panel-broadcast` screen, but 4A does not authorize or
preselect those values.
