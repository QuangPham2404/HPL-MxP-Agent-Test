## Main findings

TASK-010 decisively retains:

```text
N = 429056
NB = 3072
grid/order = 4x4 row
```

The larger-N hypothesis was reasonable because LU throughput improves with N,
but the improvement is dominated by refinement cost once the FP64 residency
boundary is crossed.

Key same-allocation evidence:

```text
N=429056:
  overall = 6.4431e+06 GFLOP/s
  LU      = 6.6784e+06 GFLOP/s / 7.85 s
  IR      = 0.29 s
  IR/LU   = 0.037
  host consumption = 0.004 GB/process
  device headroom  = 2.767 GB/process

N=454656:
  overall = 5.9212e+06 GFLOP/s
  LU      = 6.9761e+06 GFLOP/s / 8.98 s
  IR      = 1.60 s
  IR/LU   = 0.178
  host consumption = 15.024 GB/process
  device headroom  = 2.257 GB/process
```

Thus a +5.97% increase in N buys only +4.46% LU throughput but makes IR about
5.5x slower and lowers the total score by 8.10%.

Across the full sweep, LU throughput rises about 16% from N=429056 to 606208,
while IR rises 0.29 -> 14.67 s (~50.6x) and IR/LU rises 0.037 -> 0.766.
Device consumption saturates while reported host allocation grows to
136.519 GB/process. All candidates still use three refinement iterations, so
the loss is increased cost per iteration in the host-resident/staged regime,
not additional iterations or convergence failure.

The TASK-009 host-runtime improvement therefore changed the low-N IR floor but
did not remove or materially move the N/residency cliff.

## Limitations

TASK-010 is the clean causal N sweep because all five arms ran in one
allocation with only N varying. Cross-task comparisons to TASK-001/002/006/009
are contextual because node pair, process order, and/or verified host-runtime
state differ.

Reported host-memory consumption is application-level allocation evidence, not
a byte-level transfer trace. No profiler is required for the current
conclusion because phase timing, fixed iteration count, and the memory
transition already explain the score shape.
